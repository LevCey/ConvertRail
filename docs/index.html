ConvertRail documentation

A neutral settlement rail for performance marketing on Arc: conversions verified by deterministic rules, fraud refused on-chain, publishers paid per conversion in USDC.

Overview

Performance marketing is structurally adversarial. Conversions are reported by the advertiser — the same party that pays — while advertisers face fabricated and duplicated conversions from publishers. Below the top tier, settlement still runs on net-30 terms and $50–500 payout thresholds, because paying per conversion is too expensive on legacy rails.

ConvertRail closes that loop with no humans in it. An advertiser agent funds an escrow and publishes campaign rules on-chain; publisher agents submit claims with evidence; a deterministic verifier gates every claim; verified claims auto-settle unless the advertiser objects; each settled conversion is paid on its own through Circle Nanopayments; and the advertiser agent reallocates budget away from bad traffic by itself.

Architecture

ComponentResponsibility
AgentRegistryRoles: advertiser, publisher, verifier. The other two contracts gate their calls against it.
ConversionRegistryClaims, evidence hashes, verdicts. Refuses duplicate conversions itself — the transaction reverts on-chain, no verifier involved.
CampaignEscrowBudget commitment, per-publisher caps, dispute window, payout recognition, reallocation, and the true-up against the payment stream.
verifierApplies the published deterministic rules and posts verdicts on-chain. Holds no funds and has no payment capability.
settlementRecognizes the payout in escrow, then pays through Nanopayments. Reads only chain state, never the verifier directly.
agentsAdvertiser, two publishers, and a scripted fraud agent. Deterministic policies over on-chain signals.
merchant-simThe conversion source: signs conversion events. A demo stand-in for an advertiser's own reporting system.
Separation of duties is structural, not conventional. The verifier decides and the settlement module pays, and they share nothing: the verifier holds no funds and cannot initiate a payment, while settlement acts only on verdicts it reads back from the chain.

Claim lifecycle

PENDING ──verdict:approved──▶ VERIFIED ──window passes──▶ SETTLED
   │                             │
   │                             └──advertiser objects──▶ DISPUTED
   └──verdict:rejected──▶ REJECTED        (no path back to settlement)

A claim carries a nullifier — a per-conversion uniqueness tag, keccak256(campaignId ‖ conversionId) — and an evidence hash, the hash of the canonical serialization of the signed conversion event. The registry stores the nullifier on submission, so a duplicate reverts before any verification happens, and a rejected conversion id can never be resubmitted.

Verification rules

Three deterministic checks, applied in order. The verifier's configuration is hashed and committed on-chain when the campaign is created, so the rules a claim is judged by are public before it is made.

CheckWhat it catchesReason code
Duplicate nullifierA conversion someone already claimed. Enforced by the contract, so the attempt is a reverted transaction on Arc.(revert)
Evidence hashA claim whose evidence matches no signed conversion event, points at another publisher's event, or belongs to another campaign.EVIDENCE_MISMATCH
TimingConversions arriving impossibly soon after the click — bot traffic that no human generates.TIMING_ANOMALY
RateBursts beyond the configured per-publisher rate inside the window.RATE_ANOMALY
MalformedA conversion timestamped before its own click.MALFORMED_EVIDENCE

The decision core is a pure function of (claim, event, binding, policy, prior claims): identical inputs always produce identical verdicts, which is what makes a refusal auditable after the fact.

Dispute window and auto-settle

A verified claim waits out a dispute window measured in blocks. If the advertiser does not object within it, anyone may settle the claim — silence is acceptance. An objection inside the window moves the claim to DISPUTED and blocks settlement for that claim alone; an objection after the window reverts.

This is the half of the mechanism that constrains the advertiser. Deterministic rules police publisher fraud, but nothing in cryptography stops a payer from stalling — so the contract removes stalling as an option instead.

Settlement

Recognition and payment are separate steps, in that order. autoSettle recognizes the payout inside CampaignEscrow, which is where the per-publisher cap and total budget invariants are enforced; only then does the settlement module pay.

Payment is a Circle Nanopayments authorization: one EIP-3009 TransferWithAuthorization per conversion, verified and settled through the Gateway facilitator. Gateway aggregates authorizations off-chain and settles them on-chain in batches, which is what makes a $0.10 payout economical. A periodic true-up reconciles the payment stream back against escrow accounting.

The paying wallet is a Circle developer-controlled wallet. It signs each authorization through Circle's signing API and its key never appears in the repository. Because Arc is not one of Circle's managed chains, the wallet is created on the virtual EVM-TESTNET chain: Circle signs, this system broadcasts. It must be an EOA — Gateway verifies EIP-3009 by ECDSA recovery — and it never sends a transaction of its own, since provisioning credits its Gateway balance with depositFor.

Circle developer-controlled wallet952 ms

Both are instant beside the net-30 terms this replaces; CIRCLE_WALLET_ID selects between them without a code change.

Autonomous reallocation

The advertiser agent reads the same chain anyone else can — verdicts and refusals per publisher — and applies a sliding-window policy: when a publisher's refusal rate crosses the configured threshold with a minimum sample size, it moves that publisher's unspent cap headroom to the cleanest one and writes the reason code QUALITY_DIVERGENCE on-chain with the transaction.

The policy is a pure function of the ordered verdict sequence, so replaying a run reproduces the same decision. No model output participates in it, or anywhere else money moves.

Running it

Prerequisites: Node 24+, Foundry for the contracts, and an Arc testnet wallet funded from the Circle faucet.

npm install
cp .env.example .env      # set FUNDER_PRIVATE_KEY
npm run provision         # generate agent wallets, fund, register roles, deposit into Gateway
npm run demo              # drive the full adversarial loop against Arc testnet

npm run demo is an acceptance gate, not a screensaver. It exits non-zero unless the settlements land, every recognized payout has a matching payment, each deterministic rule refuses something, at least one duplicate reverts on-chain, the advertiser agent reallocates budget by itself, the fraud agent is paid nothing, and escrow accounting reconciles against the payment stream.

Each run needs an unused campaign name in demo.config.json. Conversion ids are deterministic and nullifiers are consumed on submission, so re-running an old campaign makes every honest claim revert as a duplicate.

Watch it live with the dashboard, and run the tests:

cd dashboard && npm install && npm run dev   # http://localhost:4700

npm test                    # canonical hashing, verifier rules, reallocation policy, parsers
cd contracts && forge test  # escrow accounting, dispute window, duplicate refusal, invariants

Limits and roadmap

The conversion event originates off-chain, inside the advertiser's systems, and the data producer is the paying party. That is not solved here with cryptography, and the distinction matters:

  • deterministic Publisher-side fraud — duplicates, fabricated claims, impossible timing — refused by rule, with permanent on-chain evidence.
  • mechanism Advertiser-side stalling — removed by dispute-window auto-settle, not by proof.
  • not yet Proof that the reported conversion happened at all. The verifier applies published rules with its policy hash on-chain, which is auditable, not trustless.

On the roadmap, in order:

  • Web-proof verification of conversion events (zkTLS-class suppliers), so neither side has to trust the other's systems.
  • Confidential referee — verification inside confidential compute, so neither side exposes raw campaign data.
  • Cross-chain payouts — CCTP for publishers settling elsewhere, StableFX for non-USD payout currencies.
  • Dispute resolution beyond the current terminal DISPUTED state, which records the dispute and its evidence but does not adjudicate it.
